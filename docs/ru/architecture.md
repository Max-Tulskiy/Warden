# Архитектура

Канонический текст — на русском; перевод см. [../en/architecture.md](../en/architecture.md).
Основа документа — [конституция проекта](../../.specify/memory/constitution.md); здесь
изложение подробнее и с примерами, но при расхождении конституция главнее.

## Общая схема

```
Рабочая станция (Windows 10/11, Linux)          docker-compose
┌───────────────────────────────┐        ┌──────────────────────────────┐
│ warden-agent (служба)         │        │ Caddy (TLS-прокси, порт 443)  │
│  ┌─────────────┐  ┌─────────┐ │        │   ├─ /api/* → server:8000     │
│  │ коллекторы  │→ │ буфер   │ │  HTTPS │   └─ /*     → web:80          │
│  │ (5 категорий)│ │ SQLite  │ │──────▶ │                                │
│  └─────────────┘  └─────────┘ │ исходящее  ┌────────────────────────┐  │
│         планировщик            │        │  │ FastAPI (server:8000)  │  │
└───────────────────────────────┘        │  │  ├─ агентские эндпоинты │  │
                                          │  │  ├─ операторские        │  │
                                          │  └──┴─ PostgreSQL          │  │
                                          │      (server:8000 внутри)  │  │
                                          │  веб-панель (web:80, React)│  │
                                          └──────────────────────────────┘
```

Агент никогда не принимает входящих соединений — только сам инициирует HTTPS-запросы
к серверу. Это модель «активного агента», как в Zabbix (Р-1 конституции): выбрана
потому, что реальные рабочие станции почти всегда находятся за NAT/файрволом, и прямое
подключение сервера к агенту на практике нереализуемо.

## Жизненный цикл обмена агент-сервер

1. **Регистрация (enroll).** Администратор создаёт одноразовый регистрационный токен
   в панели (`POST /api/v1/enrollment-tokens`). Агент при первом запуске обменивает
   этот токен на постоянный пер-агентный ключ (`POST /api/v1/enroll`). Сервер хранит
   только хэш ключа.
2. **Опрос задач (poll).** Каждые `poll_interval_seconds` (по умолчанию 60с) агент
   запрашивает `GET /api/v1/agents/{id}/tasks`. Сервер возвращает ожидающие задачи
   и помечает их как выданные («dispatched»).
3. **Сбор.** Независимо от опроса, коллекторы агента непрерывно пишут события
   в локальный буфер SQLite. Буфер хранит данные не дольше `retention_hours`
   (по умолчанию 8ч, не меньше 4ч — предела окна запроса).
4. **Ответ на запрос окна.** Получив задачу `window_request`, агент **повторно**
   проверяет, что окно не превышает 4 часов (двойная проверка — принцип 3
   конституции), выбирает из буфера события всех категорий за это окно и отправляет
   их через `POST /api/v1/agents/{id}/reports`.
5. **Инвентаризация и heartbeat.** Отдельно от событий, раз в
   `inventory_interval_seconds` (по умолчанию 1ч) агент отправляет снапшот
   оборудования и ПО (`POST /api/v1/agents/{id}/inventory`). Это одновременно
   обновляет отметку «последняя активность» агента.

## Модель данных сервера

| Таблица | Назначение |
|---|---|
| `agents` | Одна строка на зарегистрированный агент: хостнейм, ОС, хэш ключа, статус, последняя активность |
| `enrollment_tokens` | Одноразовые токены регистрации с временем жизни |
| `tasks` | Очередь задач (пока только `window_request`) со статусом pending/dispatched/completed/failed |
| `events` | События по категориям (`removable_media`, `printing`, `processes`, `web`), привязаны к задаче, за ответ которой получены |
| `inventory_snapshots` | Полные снапшоты оборудования/ПО, никогда не перезаписываются (append-only) |
| `inventory_changes` | Отдельные записи об обнаруженных изменениях (добавлено/удалено/изменено) |
| `operators` | Учётные записи администраторов панели; `token_version` — счётчик, увеличением которого завершаются все сеансы оператора |
| `audit_log` | Журнал всех значимых действий: регистрация, выдача задач, вход, изменения конфигурации; читается в панели на экране «Журнал» |

### Детектор изменений конфигурации

При каждом снапшоте инвентаризации сервер вычисляет SHA-256 канонической
(с сортированными ключами) JSON-формы `{hardware, software}` и сравнивает его
с хэшем последнего сохранённого снапшота той же станции:

- хэши совпадают → только обновляется `last_seen_at`, новой записи об изменении нет;
- хэши расходятся (или это первый снапшот станции) → сохраняется новый снапшот
  **и** отдельная запись в `inventory_changes` с постатейным diff по верхнеуровневым
  ключам разделов `hardware` и `software`.

Так реализовано требование задания «отдельно хранить сведения об оборудовании и ПО
с целью выявления изменений конфигурации» — снапшоты не подменяют друг друга,
история видна целиком, а факт изменения виден администратору сразу.

## Отчёты и настройки панели

**Отчёт по всем станциям** (`GET /api/v1/events`) показывает события одной, нескольких
или всех станций за произвольный период. Параметры: `start` и `end` (обязательные),
`agent_id` (можно повторять), `category`, `limit`/`offset`. Период полуоткрытый —
`[start, end)`, как и проверка границ окна при приёме отчёта агента. Строки идут в
порядке `(occurred_at, id)`: так постраничная выдача не теряет и не повторяет события
с одинаковым временем. Каждая строка несёт `agent_id` и *текущее* имя станции (имя не
версионируется). Ограничение в 4 часа к отчёту не относится: оно действует на запрос,
который сервер ставит агенту (принцип 3), а отчёт только читает уже сохранённое,
поэтому недельный период допустим. Для выборки по времени на `events` есть индекс
`ix_events_occurred_at`.

**Политика сервера** (`GET /api/v1/policy`) — только чтение: предел окна запроса, срок
действия токена регистрации и сессии, минимальная длина пароля, лимиты отчёта агента,
снимка инвентаря и страницы выдачи. Значения берутся оттуда, где они реально
применяются, а ответ — явный список полей, а не выгрузка настроек: секрет
(`jwt_secret`, строка подключения к БД) не может попасть в него случайно. Менять эти
значения из панели нельзя — только конфигурацией сервера.

**Отключение станции** (`PATCH /api/v1/agents/{id}` со статусом `disabled` или `active`).
Проверку выполняет уже существующая зависимость `require_agent`: агент не в статусе
`active` получает тот же 401, что и при неверном ключе. Ключ при отключении не
меняется, поэтому повторное включение возвращает станцию в работу без новой
регистрации. Реальная смена статуса пишется в журнал (`agent.disabled`,
`agent.enabled`); повторная установка того же статуса — нет. Сам агент при 401 не
падает: исключение перехватывает цикл планировщика, ошибка попадает в его локальный
журнал, опрос продолжается.

## Журнал аудита

Сервер пишет в `audit_log` каждое значимое действие (принцип 8): регистрацию станции,
выдачу задач, приём отчёта и снимка инвентаря, обнаруженное изменение конфигурации,
вход и смену пароля оператора, запрос окна, выпуск токена регистрации, отключение и
включение станции. Прочитать журнал можно в панели («Журнал») или через
`GET /api/v1/audit`.

Параметры запроса: `start` и `end` (обязательные), `actor`, `action`, `limit`/`offset`.
Период полуоткрытый — `[start, end)`, как и у отчёта по станциям. Строки идут от новых
к старым в порядке `(occurred_at DESC, id)`: так постраничная выдача не теряет и не
повторяет записи с одинаковым временем. `actor` сравнивается точно и может быть именем
оператора, идентификатором станции или именем хоста, присланным при регистрации.
`action` — либо точный код (`operator.login`), либо группа, то есть часть кода до точки
(`operator` — все `operator.*`). Обычный префикс строки вернул бы вместе с
`operator.login` ещё и `operator.login_failed`, поэтому группа сопоставляется только
по границе точки. Ограничение в 4 часа к чтению журнала не относится: оно действует на
запрос, который сервер ставит агенту (принцип 3). Для выборки по времени на
`audit_log` есть индекс `ix_audit_log_occurred_at`.

Панель показывает действия русскими названиями; код, для которого названия нет
(например, добавленный более новой версией сервера), выводится как есть, запись не
скрывается. Идентификатор станции в колонках «Кто» и «Объект» заменяется именем хоста,
если список станций загрузился. Чтение журнала само в него не пишется — как и другие
чтения в панели.

## Аутентификация

Два независимых механизма (принцип 5 конституции):

- **Агенты** — заголовок `X-Agent-Key` с постоянным ключом, выданным при регистрации.
  Сервер хранит только SHA-256 хэш ключа и сверяет его через `hmac.compare_digest`
  (константное время сравнения). Ключ обязан совпадать именно с тем `agent_id`,
  что указан в пути запроса — иначе ключ одного агента подошёл бы для эндпоинтов
  любого другого.
- **Операторы** (панель) — JWT, выданный по логину/паролю
  (`POST /api/v1/auth/login`). Пароль хранится через Argon2id.

Каждая неудачная попытка входа пишется в `audit_log` как `operator.login_failed`
(только причина — «неизвестный пользователь» или «неверный пароль», без самого
пароля), а после пяти неудач за пять минут для этого имени пользователя сервер
отвечает 429 и пишет `operator.login_throttled` — даже верный пароль не обходит
активную блокировку (`services/throttle.py`). Счётчик живёт в памяти процесса:
для поставляемого развёртывания (uvicorn без `--workers`) это точно, но при
нескольких воркерах или репликах эффективный лимит умножается на их число, а
при перезапуске обнуляется — честно задокументированное ограничение (принцип 10
конституции), а не решённая задача.

Оператор меняет свой пароль через `POST /api/v1/auth/password` (нужен действующий
токен). Сервер заново проверяет текущий пароль через Argon2id; новый пароль — не короче
12 символов, не длиннее 1024 и отличается от текущего. Неверный текущий пароль — 400
(не 401, чтобы панель не принимала это за истёкшую сессию) и запись
`operator.password_change_failed`; успешная смена — `operator.password_change`.
Повторные неудачи ограничивает тот же механизм, что и вход (пять за пять минут, ответ
429, `operator.password_change_throttled`), но под отдельным ключом: владелец
украденного токена не сможет этим эндпоинтом заблокировать вход настоящему оператору.
Сами пароли в журнал не попадают. Учётную запись из `WARDEN_SEED_ADMIN_*` бутстрап
создаёт только при пустой таблице операторов, поэтому перезапуск контейнера прежний
пароль не возвращает.

**Сеансы.** Сеанс оператора — JWT с полями `sub`, `exp` и `ver`, где `ver` — значение
`operators.token_version` на момент выдачи. `require_operator` отвечает тем же 401,
что и на любой недействительный токен, если `ver` отсутствует, не является целым
числом или не равно текущему значению у оператора (решение D-9 конституции). Поэтому
увеличение одного числа завершает сразу все сеансы оператора. Его увеличивают две
операции. Успешная смена пароля отвечает 200 и токеном для новой версии: сеанс, с
которого пароль сменили, продолжается, а остальные получают 401 при следующем
обращении. `POST /api/v1/auth/logout-all` (204) завершает все сеансы, включая
текущий, и пишет `operator.sessions_revoked`. Неудачная смена пароля (400, 422, 429)
ничего не завершает. Увеличение — один SQL-запрос `token_version = token_version + 1`,
а не чтение и запись в Python: два одновременных запроса не потеряют отзыв. Срок
сеанса (`jwt_expire_minutes`, по умолчанию 8 часов) от этого не меняется. Токен,
выданный до появления версий, поля `ver` не содержит и отклоняется один раз после
обновления сервера: оператор просто входит заново.

Панель обрабатывает отказ в одном месте. Когда сервер отвечает 401 на запрос **с
токеном**, API-клиент вызывает зарегистрированный обработчик: он очищает сеанс, а
`RequireAuth` ведёт на экран входа с сообщением «Сеанс завершён. Войдите снова.» Вход
с неверным паролем (401 без токена) и неверный текущий пароль при смене (400) отказом
сеанса не считаются. Отдельный сеанс завершить нельзя — только все сразу.

Весь трафик снаружи идёт по TLS — терминируется на обратном прокси Caddy
(`docker-compose.yml`, `Caddyfile`), не на самом сервере приложения.

## Коллекторы агента

Каждая категория событий имеет платформенный бэкенд, выбираемый в рантайме
(`warden_agent.collectors.registry`, принцип 1 конституции — весь ОС-специфичный
код изолирован внутри `linux.py`/`windows.py` конкретного коллектора):

| Категория | Linux | Windows |
|---|---|---|
| Оборудование и ПО | `psutil` (железо) + `dpkg-query`/`rpm` (пакеты) | `psutil` (железо) + реестр `...\Uninstall` |
| Съёмные носители | `/sys/block/*/removable` + `/proc/mounts`, без внешних утилит | `pywin32`: `GetLogicalDriveStrings`/`GetDriveType` |
| Печать | журнал CUPS `page_log` | Event ID 307 канала `PrintService/Operational` |
| Процессы | `psutil.process_iter`, кроссплатформенно | то же |
| Веб-сайты | история Chromium-браузеров и Firefox (SQLite-копия, т.к. файл занят браузером) | то же |

Логика превращения сырых данных в события (парсинг строки `page_log`, разбор
записи реестра, diff множеств устройств) вынесена в чистые функции и покрыта
юнит-тестами на фикстурах на любой платформе. Сами системные вызовы (`winreg`,
`pywin32`) — тонкая обвязка, проверенная вживую только там, где это было
технически возможно (раздел VI конституции и [usage.md](usage.md)).

## Границы

Полный список — раздел V конституции. Ключевое:

- сайты — только из истории браузеров, не перехват трафика;
- печать — только через системный спулер, не прямая печать в устройство;
- ответ на запрос приходит с задержкой до одного интервала опроса, не мгновенно;
- история браузера видна только для той учётной записи ОС, под которой запущена
  служба агента — на общей многопользовательской машине это не покрывает всех
  пользователей одновременно;
- один отчёт агента ограничен 10 000 событий, снимок инвентаря — 10 000 записей
  оборудования и 10 000 записей ПО каждое; чтение списка событий за день и
  таймлайна изменений отдаёт не более 2000 записей за раз (по умолчанию 500), с
  пагинацией `limit`/`offset` — на реальной нагрузке (окно ≤4 часа, опрос раз в
  минуту) этого хватает с большим запасом, но при превышении лишние записи не
  видны без запроса следующей страницы;
- отчёт по всем станциям читает только то, что уже лежит на сервере, а события
  попадают туда исключительно по запросам окна (принцип 2). Это не «вся активность
  парка за период»: у станции, для которой окно не запрашивали, отчёт пуст, даже если
  событий на ней было много;
- повторные запросы пересекающихся окон сохраняют одно и то же событие дважды —
  дедупликации при приёме нет, поэтому отчёт (как и отчёт за день) может показать
  дубликаты;
- завершить можно только все сеансы оператора сразу и только самому оператору: один
  сеанс нельзя ни увидеть, ни завершить отдельно, а украденный токен работает, пока
  оператор не сменит пароль, не завершит все сеансы или пока токен не истечёт (по
  умолчанию 8 часов). Кражу сервер не обнаруживает. Сеанс, выданный до появления версий,
  отклоняется один раз после обновления;
- журнал аудита неполон: он фиксирует изменения и входы, но не чтение (отчёты, списки
  станций, сам журнал) и не отказы, которые получает отключённая станция;
- журнал не защищён от правки: он «только дописывается» лишь по тому, как с ним работает
  код сервера. Ни триггера, ни ограничения прав на уровне БД нет, поэтому тот, у кого
  есть доступ на запись в PostgreSQL, может изменить или удалить строки, и панель этого
  не обнаружит;
- актор записи не всегда прошёл проверку: для отклонённой регистрации
  (`agent.enroll_rejected`) это имя хоста, присланное вызывающим, у которого на этот
  момент нет действительного токена. Панель выводит его как текст, а не как разметку;
- отключённый агент продолжает раз в интервал опроса обращаться к серверу и получать
  401, записывая ошибку в свой локальный журнал; сервер эти отказы в аудит не пишет
  (это около 1440 записей в сутки на станцию). Запрос окна на отключённую станцию
  по-прежнему можно поставить: он останется в очереди до повторного включения, после
  чего агент ответит из уже частично очищенного буфера.

## Ответы на типовые вопросы

**Почему не WebSocket/постоянное соединение?** Дало бы иллюзию мгновенного отклика,
но потребовало бы Redis/pub-sub для маршрутизации и обработки переподключений —
несоразмерная сложность против выигрыша при объёме запросов этого комплекса
(окна измеряются часами, а не секундами).

**Почему сервер не может сам достучаться до агента?** Рабочая станция почти всегда
за NAT или файрволом организации; входящее соединение к ней с сервера в общем
случае технически нереализуемо. Активная модель (агент сам приходит к серверу)
работает в этих условиях без исключений.

**Что мешает агенту отдать данные за произвольный период?** Само по себе —
ничего, поэтому проверка ≤4ч и продублирована: на сервере при постановке
запроса и на агенте при его исполнении. Ошибка в одной части не даёт обойти
